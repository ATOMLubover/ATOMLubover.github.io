## 简述

在设计分布式微服务的业务开发中，为了达成最终一致，我们通常需要加入本地消息表以完成简化的投递型分布式事务。

为了能够总是严谨地开发出能够解决 95% 最终一致性分布式事务场景的本地消息表机制，本文将会一步一步拆解、说明如何构建一个最精简、类似 MQ 的本地消息表。

## 投递端抽象

### 投递 Oper 抽象

本地消息表实际上就是一个可以在本地事务中运行的 MQ，所以它的投递接口可以及其简单。

从 action 的思路来考虑，我们就是需要一个延迟执行的动作 `Defer`，即：

```rust
pub struct Defer {
    pub task: Task,
}
```

其中 `Task` 是要具体执行的任务（通常代表着要被序列化到数据库的信息 + 控制元数据）。之所以不直接将 `Task` 的字段直接放在 `Defer` 中，是因为后续会引入批处理的 `DeferBatch`，它需要接受 `tasks: &[Task]`。

### Task 抽象

那么接下来，重点转移到 `Task` 结构体该如何设计。

通常我们在使用本地消息表时，会希望能够控制如下两种元数据：

- task 的 ID。
- task 的延迟。

这两者一个决定了一个任务是否能够被唯一标识，一个提供了延迟任务的功能。所以，我们可以初步写出一个 task 的框架代码：

```rust
pub struct Task<'a, I: AsRef<str>> {
    pub id: &'a I,
    pub delay: Option<Duration>,
}
```

:::note
需要注意的是，这里任务之所以要唯一标识，其实是一种将 ID 分配权上提的思路。因为在分布式系统中，我们通常不会让一个业务实体的 ID 交由数据库层自己分配，以防止碰撞等问题。
:::

在解决完元数据问题后，我们就可以将实际的业务 payload 也加入字段当中了。考虑到我们在开发的是一个框架，所以自然地要使用泛型参数来表示 payload：

```rust ins={4}
pub struct Task<'a, I: AsRef<str>, P: ?Sized> {
    pub id: &'a I,
    pub delay: Option<Duration>,
    pub payload: &'a P,
}
```

:::tip
这里全部采用借用的原因主要是，实际上基于数据库实现的本地消息表通常都只需要不可变借用的 `payload` 来进行序列化，所以我们无需获取它的所有权，以防止让业务层出现不必要的开销。
这一点在我开发的 PopRaKo Server 服务器中体现得尤为明显，基本所有的 repo action 的参数都采用的是不可变借用而非获取所有权的方式传递。
:::

这样改造之后，`Defer` 也可以自然修改为：

```rust
pub struct Defer<'a, I, P> {
    pub task: Task<'a, I, P>,
}
```

`DeferBatch` 也可以很简单地构造出来：

```rust
pub struct DeferBatch<'t, 'a, I, P> {
    pub tasks: &'t [Task<'a, I, P>],
}
```

### 接入事务框架

最终，为了接入面向 action 的事务框架，我们需要为 `Defer` 和 `DeferBatch` 实现 `Oper` trait。由于 `Oper` trait 需要一个返回值，而业务系统通常最终也需要这个返回值，所以我们再为两者添加一个范型参数 `O`：

```rust
pub struct Defer<'a, I, P, O> {
    pub task: Task<'a, I, P>,
    _m: PhantomData<fn(O)>,
}

pub struct DeferBatch<'t, 'a, I, P, O> {
    pub tasks: &'t [Task<'a, I, P>],
    _m: PhantomData<fn(O)>,
}
```

最后实现：

```rust
impl<'a, I, P, O> for Defer<'a, I, P, O> {
    type Output = O;
}

impl<'t, 'a, I, P, O> for DeferBatch<'t, 'a, I, P, O> {
    type Output = O;
}
```

这样，我们就已经完成了对于投递端的抽象，最终我们只需要一个对应的 `PromProd` 封装一下提供给 usecase 使用即可：

```rust
pub trait PromProd<C>: 
    for<'a> Step<Defer<'a, String, TaskPayload, ()>, Context = C, Error = BaseError>
    + for<'t, 'a> Step<DeferBatch<'t, 'a, String, TaskPayload, ()>, Context = C, Error = BaseError> 
{}
```

:::tip
`PromProd` 中的 `Defer` `DeferBatch` 都已经单态化，这样会减少范型数量更加方便使用。并且对于一般的业务服务器来说，ID 和 payload 的类型确实是全局统一的，因此直接单态化并不影响整体的表达力。
:::

## 消费端抽象

解决了简单的投递端抽象之后，接下来要解决的就是复杂的消费端抽象了。

我们仔细思考常见的 MQ 所提供的能力，其实主要包含如下几个方面：

- 多消费单元，消费单元内可靠串行，消费单元间允许并发
- topic 内一条消息消费时间有上限，超时回收
- 支持消息重试，有死信队列存放反复失败的消息

为了解决这些问题，同时兼顾性能，接下来将一步步构建功能，最后再逐步完成优化。

:::note
需要注意的是，这里要求 `Task` 必须可以重复消费，这在业务上要求任务的执行方/消费方是幂等的。幂等需要 `payload` 内蕴的数据以及对应的 handler 共同保证。
此处要求可以幂等消费，主要这是维持最终一致性最简单的方案：通过 idiomatic consumption + at-least-once delivery 实现等效 exactly-once delivery。
:::

### 消息 entity 初步抽象

根据上文所述的三条规则，我们可以以 entity-first 的思路，先思考实体（也就是数据格式）该如何设计。

考虑到我们最终是存储在关系型数据库中，所以可以扁平化为如下的 schema：

```sql
CREATE TABLE IF NOT EXISTS t_local_message (
    -- 上文中 Task 所指定的 `id` 字段
    id TEXT PRIMARY KEY,
    
    -- 从简起见，topic 就是最小消费单元
    topic TEXT NOT NULL,
    
    -- 当前消息的处理状态
    status TEXT NOT NULL,
    -- 已重试次数
    retried_count INT NOT NULL DEFAULT 0,

    -- 朴实无华的序列化后的 payload
    payload TEXT,
        
    -- 从 delay 转换得到的可见时间点
    visible_at TIMESTAMPTZ NOT NULL,
);
```

:::tip
之所以不在 topic 下再构建一层 partition 层，主要是因为单一业务服务器对一个 topic 只有一个消费者（组），我们不需要为一个消息流维护多个 offset。这样可以极大程度地简化消费和清理的实现。
:::

可以发现，其实结构与 `Task` 几乎一致，主要包括：

- 全局控制元数据：`id`、`topic`
- 消息状态元数据：`status`、`visible_at`、`retried_count`
- 消息载荷：`payload`

### 业务消费逻辑

现在有了最基础的数据，我们该开始编写对应的逻辑了。为了简便理解，我们将从接口行为和状态机流转的思路来一步步实现。

我们来思考一下，无状态的业务服务器需要与有状态的数据库存储的数据之间，有怎样的交互契约。或者更准确的说，数据库需要给业务服务器提供哪些读写接口。

显然，业务服务器上运行的消费者需要做如下几个操作：

- 从一个里 `topic` 领取一个 `Task`
- 标记一个 `Task` 已完成

用代码可以演示如下：

```rust
pub trait LocalMessageRepo {
    pub async fn claim(&self) -> Result<LocalMessage, BaseError>;
    pub async fn mark_completed(&self, id: &str);
}
```

需要注意的是，这里没有创建事务，因为假设领取需要在事务内，则代表着标记完成也需要放在事务内，这就会把 **消费过程**（通常需要调用外部 RPC）也囊括在内。这种长事务是需要审慎加入的，所以此处采用状态机 + 无事务 + 外部补偿的方法保证正确性。
