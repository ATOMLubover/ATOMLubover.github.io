## 简述

在 Go 中，我们通常会直接为 service 注入持有 connection pool 的 repo 实例。这是非常符合直觉的设计，能够让非事务的 repo action 简单地被调用执行，service 不用自己每次调用 repo 都注入一个 connection 上下文，自然也就不用知道 connection pool 这种实现细节。

然而，一个自绑定 connection pool 的 repo 实例通常会被多个 service usecase 复用。如果既没有接受外界 transaction 上下文的机制，也没有其他事务协调机制，service 就无法指定其中一组调用参与同一个事务。这种直接注入自持有 connection pool 的 repo 的 API 设计，还不足以完成动态 transaction 上下文注入。

为了解决这个问题，我设计了一种新的事务上下文注入范式，在编译期确定 repo 与 transaction 上下文的类型关系，在运行时由协调器提供上下文，以实现类型安全、无须细节泄漏的显式事务上下文注入。

---

## 自持有 connection pool 的 repo 实例的问题

通常，自持有 connection pool 的 repo 的实现、使用代码如下：

```rust title="src/repo/wallet.rs"
#[async_trait(?Send)]
pub trait WalletRepo {
    async fn debit_balance(
        &self, 
        wallet_id: i64, 
        amount: i64
    ) -> Result<(), BaseError>;

    async fn credit_balance(
        &self, 
        wallet_id: i64, 
        amount: i64
    ) -> Result<(), BaseError>;
}
```

```rust title="src/repo_impl/wallet.rs"
pub struct WalletRepoImpl {
    pool: ConnPool,
}

#[async_trait(?Send)]
impl WalletRepo for WalletRepoImpl {
    // ...
}
```

```rust title="src/service/wallet.rs"
pub async fn transfer_balance(
    wallet_repo: Arc<dyn WalletRepo>,
    sender_id: i64,
    receiver_id: i64,
    amount: i64,
) -> Result<(), BaseError> {
    wallet_repo.debit_balance(sender_id, amount).await?;
    wallet_repo.credit_balance(receiver_id, amount).await?;
    Ok(())
}
```

:::note
本文所有的代码不保证完全合乎语法，核心是为了通过代码这种确定的形式辅助阐述和读者理解。
:::

上述代码在不需要任何事务时会非常简便，然而对于  `debit_balance` 和 `credit_balance` 这一对操作，我们通常必须开启事务。而一旦引入事务，一切就变得棘手了起来。 

我们假设有下述 usecase 函数需要开启事务：

```rust {"初始非事务上下文":2-3} ins={"切换到事务上下文":4-9} {"回到非事务上下文":10-11}
pub fn run_partial_transaction() {

    // Step 1: xxx
    
    // Step 2: transaction
    {
        // Step 2.1: xxx
        // Step 2.2: xxx
    }
    
    // Step 3: xxx
}
```

我们会立刻发现，我们缺少一个机制，让应该在事务中执行的函数 **知道** 自己要在事务中运行。

比如：

```rust
async fn debit_balance(
    &self, 
    wallet_id: i64, 
    amount: i64
) -> Result<(), BaseError>;
```

完全没有一个参数（比如 `is_in_transaction: bool` 或者 `context: Option<TransactionContext>`）或者是变体（比如 `debit_balance_in_transaction()`，能够让 service 控制 repo 执行事务版本的操作。

这里不难注意到业务代码实现事务时的一个特性：**事务的边界由业务 usecase 决定，但是由 repo 实际执行**。

所以这就必然需要实现两个核心机制：

- service 通知 repo 处于 transaction 上下文
- repo 根据 transaction 上下文信息适应地执行

---

## 上下文概念的抽象

对于常见 RDBMS 实现的 repo impl 来说，“根据 transaction 上下文信息” 适应的执行相对比较简单。大部分的 Rust ORM 抽象都是直接在一个特定的 `Connection` 对象上执行 SQL，本身就不关心这个连接是否是在一个开启了事务的 session 里的。因此上一节最后的问题相对很好解决。

因此最后的两个问题，可以整合为对第一个问题的更简单描述：我们需要实现的核心机制是 **“service 给 repo 提供上下文信息，让它执行事务版本的 action”**。这里的上下文信息，则通常是一个预先开启了事务的 connection。

为了达成这个机制，我接下来将一步一步渐进式地给出最终我们希望的系统形态。

### 为 repo action 提供可空 context 参数

上文我们提到，我们可能可以通过两种大方向来实现从 service 层到 repo 层自上而下的通知，一种是添加参数，一种是提供函数变体。

考虑到为一段逻辑提供两个变体（比如 `debit_balance()` 和 `debit_balance_in_transaction()`）会略微有些麻烦，所以我们暂时先考虑最简单的增加一个参数的方法。

:::tip
基于可空参数的方法会有一定的运行时开销（检查是否为空然后走不同的分支），所以最合理的方案会回到 **类似** 双变体编译期分发的方法，不过会更加优雅。限于篇幅限制，本文暂时不会设计到最终方案的改进设计。
:::

那么，以 `WalletRepo` 为例，我们就可以有下述的修改：

```rust ins={5,12}
#[async_trait(?Send)]
pub trait WalletRepo {
    async fn debit_balance(
        &self,
        context: Option<&mut Context>,
        wallet_id: i64, 
        amount: i64
    ) -> Result<(), BaseError>;

    async fn credit_balance(
        &self, 
        context: Option<&mut Context>,
        wallet_id: i64, 
        amount: i64
    ) -> Result<(), BaseError>;
}
```

:::tip
之所以这里采用的标识符名字叫做 `Context`，主要是为了通用性，因为不是所有的 ORM 所需要的 transaction 上下文都建模为 connection。
:::

然而，读者如果自己尝试一下不难发现，这样子 repo 所写出的 `Context` 会是一个具体类型，进而导致 service 层接触到这个具体类型的实现细节。代码类似如下：

```rust
// 在 service 函数当中根据业务逻辑构造 context
let context = build_transaction_context().await?;

wallet_repo.debit_balance(context, /* .. */).await?;
wallet_repo.credit_balance(context, /* .. */).await?;
```

### 抽象 context 为关联类型

那么，如何不让这个具体类型泄漏到 service 层呢？自然的想法是将其转换为泛型参数，而 service 不为这个泛型参数添加任何约束。

进一步地，我们需要思考这个泛型参数的约束位置放在哪里。不难发现，对于 service 和 repo 接口层，我们完全不需要 **直接使用** 这个泛型，不需要给他添加任何约束；对于每一个 repo 的具体实现者来说，它又是唯一确定的。

这就需要使用到 associated type 了。我们可以为 `WalletRepo` 这样的 repo 添加一个关联类型 `Context`，允许将这个具体类型交给实现者来确定：

```rust ins={3}
#[async_trait(?Send)]
pub trait WalletRepo {
    type Context;

    async fn debit_balance(
        &self,
        context: Option<&mut Context>,
        wallet_id: i64, 
        amount: i64
    ) -> Result<(), BaseError>;

    async fn credit_balance(
        &self, 
        context: Option<&mut Context>,
        wallet_id: i64, 
        amount: i64
    ) -> Result<(), BaseError>;
}
```

之后在 service 层调用将类似：

```rust ins={2,4,9,12,14} del={1,3,11,13}
pub async fn transfer_balance(
pub async fn transfer_balance<C>(
    wallet_repo: Arc<dyn WalletRepo>,
    wallet_repo: Arc<dyn WalletRepo<Context = C>>,
    sender_id: i64,
    receiver_id: i64,
    amount: i64,
) -> Result<(), BaseError> {
    let context = build_transaction_context().await?;
    
    wallet_repo.debit_balance(sender_id, amount).await?;
    wallet_repo.debit_balance(context, sender_id, amount).await?;
    wallet_repo.credit_balance(receiver_id, amount).await?;
    wallet_repo.credit_balance(context, receiver_id, amount).await?;
    
    Ok(())
}
```

## 构建事务管理器

在上一节，我们暂时使用概念性的 `build_transaction_context` 函数获取上下文，但既然 service 不应依赖 `Context` 的具体类型，它也就不应该自行决定如何构造这个上下文。此外，我们还需要一个外界注入的能力，来统一管理事务的开启、提交与回滚。

因此，需要引入一个事务管理器：由它提供自己所声明的 `Context`，并在受控的事务范围内将上下文交给业务代码和 repo 使用。

参考大部分 ORM 都提供的闭包式 API，我们可以初步设计一个这样的 `Nucl` 管理器：

```rust
// `Step(E)` 表示闭包返回的操作错误，`Backend(BE)` 表示事务管理过程中的错误
pub enum NuclError<E, BE> {
    Step(E),
    Backend(BE),
}

#[async_trait(?Send)]
pub trait Nucl {
    type Context;
    type Error; // 开启、提交或回滚事务时的后端错误

    async fn coord<F, T, E>(&self, f: F) -> Result<T, NuclError<E, Self::Error>>
    where
        F: for<'cx> AsyncFnOnce(&'cx mut Self::Context) -> Result<T, E>;
}
```

它同样声明了 `Context` 关联类型，这意味着它可以在编译期就让类型系统保证它所驱动的事务与 repo 所期望的事务上下文是匹配的。对应的 service 代码类似：

```rust ins={2-3,12-16} del={1,9-11}
pub async fn transfer_balance<N: Nucl<Context = C>, C>(
pub async fn transfer_balance<N: Nucl<Context = C>, C>(
    nucl: &N,
    wallet_repo: Arc<dyn WalletRepo<Context = C>>,
    sender_id: i64,
    receiver_id: i64,
    amount: i64,
) -> Result<(), BaseError> {
    let context = build_transaction_context().await?;
    wallet_repo.debit_balance(context, sender_id, amount).await?;
    wallet_repo.credit_balance(context, receiver_id, amount).await?;
    nucl.coord(async move |context| {
        wallet_repo.debit_balance(context, sender_id, amount).await?;
        wallet_repo.credit_balance(context, receiver_id, amount).await?;
    })
    .await?;

    Ok(())
}
```

 `Nucl` 的实现者将声明自己所能够提供的 `Context`，并且它将自己处理在接受这个闭包之后，如何开启事务、如何提交、如何回滚，以及一些异步取消的安全问题。

这样，在 service 层通过两个 `Context = C` 就成功类型安全地桥接了 `Ncul` 和 `WalletRepo`，且完全没有知道任何实现细节。

## 总结

至此，我们将整个事务流程控制分为了指责清晰的三个部分：

- 事务上下文提供者：`Nucl` 事务管理器
- 事务上下文消费者：repo 层
- 事务协调与上下文传递：service 层

整个架构泾渭分明，没有任何下层细节向上的扩散，且完全符合静态类型安全。

在此基础上，还可以扩展更加 action-oriented 的 API 设计增强复用性，还可以通过类型系统实现事务隔离级别的编译期安全匹配。

## 题外话：为什么基于 Spring Boot 的应用很少体会到事务掣肘

在使用 Spring Boot 的应用中，事务管理通常由 Spring Framework 提供。在常见的命令式 JDBC 事务模型里，Spring 将事务资源绑定到当前线程，数据访问组件通过 Spring 的事务感知机制取得对应的连接，因此 service 不必逐次传递连接参数。

Spring 提供 JDBC、JPA、Hibernate 等集成，MyBatis-Spring 也接入了 Spring 已有的事务管理机制。事务参与关系由框架配置和运行时协调，service 的函数签名不会显式表达这种关系。这就是典型的静态类型不安全的设计。

本文关注的是通过显式参数、关联类型和借用表达类型安全的事务上下文关系，所以不展开这种框架托管的隐式上下文方案。
