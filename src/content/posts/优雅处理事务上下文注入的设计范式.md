## 简述

在 Go 中，我们通常会直接为 service 注入持有 connection pool 的 repo 实例。这是非常符合直觉的设计，能够让非事务的 repo action 简单地被调用执行，service 不用自己每次调用 repo 都注入一个 connection 上下文，自然也就不用知道 connection pool 这种实现细节。

然而，一个自绑定 connection pool 的 repo 实例通常会被多个 service usecase 复用。如果既没有接受外界 transaction 上下文的机制，也没有其他事务协调机制，service 就无法指定其中一组调用参与同一个事务。这种直接注入普通 repo 的 API 设计，还不足以完成动态 transaction 上下文注入。

为了解决这个问题，我设计了一种新的事务上下文注入范式，在编译期确定 repo 与 transaction 上下文的类型关系，在运行时由协调器提供上下文，以实现类型安全、按需取用、无须细节泄漏的显式事务上下文注入。

## 传统事务上下文注入方式剖析

### 基于 interface 的动态分发方式基准线

为了下文方便叙述和对比，此处先给出一些 baseline 代码，它们根据传统的设计范式构建。

最常见的基于 interface 的动态分发的代码大致如下：

```rust title="src/repo/wallet.rs"
#[async_trait(?Send)]
pub trait WalletRepo {
    async fn debit_balance(
	    &self, 
	    wallet_id: i64, 
	    amount: i64
	) -> Result<(), BaseError>;

    async fn credit_balance(
	    &self, 
	    wallet_id: i64, 
	    amount: i64
	) -> Result<(), BaseError>;
}
```

```rust title="src/repo_impl/wallet.rs"
pub struct WalletRepoImpl {
    pool: ConnPool,
}

#[async_trait(?Send)]
impl WalletRepo for WalletRepoImpl {
    // ...
}
```

```rust title="src/service/wallet.rs"
pub async fn transfer_balance(
    wallet_repo: Arc<dyn WalletRepo>,
    sender_id: i64,
    receiver_id: i64,
    amount: i64,
) -> Result<(), BaseError> {
    wallet_repo.debit_balance(sender_id, amount).await?;
    wallet_repo.credit_balance(receiver_id, amount).await?;
    Ok(())
}
```

### 事务上下文注入问题

在开发 PopRaKo Server 的过程中，我逐渐发现，仅靠上述接口的设计范式无法满足跨多个 repo action 的事务需求。

这个矛盾的核心生发点就是，**事务上下文的动态注入**。

也就是说，在这个例子中，repo 自行选择连接，service 却负责决定哪些操作必须一起成功或失败。单靠 `async fn debit_balance(&self, wallet_id: i64, amount: i64) -> Result<(), BaseError>` 这样的调用接口，service 无法指定两次操作使用同一个事务。

为了解决这个问题，必须修改 repo 层及其协调接口，让 service 能显式指定事务范围。

### 传统范式下可能的解决方法

对 API 的修改思路通常有两种：

- 让 repo 的函数接口额外接受一个可空的 context 参数。
- 为 service 额外注入一个可以提供同一事务下 repo 的生成器。

接下来我将递进地说明这些解决方案，以逐步阐述其问题所在。

:::note
我们默认 service 层及 repo 层的约束与边界是：
- service 决定事务的范围
- service 不依赖 transaction 上下文的具体类型，但可以声明上下文与 repo 之间的类型关系
- 类型系统应该能够保证 repo 类型和上下文是匹配的
- 多个 repo action 可以放入一个事务
- 事务的开始、结束由一个机制统一管理
:::

#### 添加一个可空 context 参数

我们这里复用上文的 `WalletRepo` 做演示：

```rust ins={5,12}
#[async_trait(?Send)]
pub trait WalletRepo {
    async fn debit_balance(
        &self,
        context: Option<&mut Context>,
        wallet_id: i64,
        amount: i64,
    ) -> Result<(), BaseError>;

    async fn credit_balance(
        &self,
        context: Option<&mut Context>,
        wallet_id: i64,
        amount: i64,
    ) -> Result<(), BaseError>;
}
```

然而需要注意的是，这个版本里的 `Context` 指的是数据库连接或事务对象的具体类型。service 只负责传递它，并不需要调用它的数据库操作。但像这样直接把具体类型写进 repo 接口，就会让 service 在组织事务时接触到实现细节，这显然破坏了我们希望保留的 service 与具体实现细节之间的隔离。

那如果我们就是要去除掉 service 层对 `Context` 具体类型的感知呢？一种直接的尝试是将其擦除为 `std::any::Any`：

```rust ins={5,12}
#[async_trait(?Send)]
pub trait WalletRepo {
    async fn debit_balance(
        &self,
        context: Option<&mut dyn std::any::Any>,
        wallet_id: i64,
        amount: i64,
    ) -> Result<(), BaseError>;

    async fn credit_balance(
        &self,
        context: Option<&mut dyn std::any::Any>,
        wallet_id: i64,
        amount: i64,
    ) -> Result<(), BaseError>;
}
```

但是，这种方法把 repo 与上下文是否匹配的检查推迟到了运行时：repo 必须尝试向下转型，才能知道收到的上下文是否可用。这是一种没有必要的 overhead。

上下文提供方与 repo 原本可以通过类型系统建立关系，擦除为 `Any` 后却丢失了这份静态保证。

:::note
另外，`Any` 要求被擦除的类型满足 `'static`，因此也不能直接容纳内部借用了局部连接的事务对象。
:::

:::tip
在 Go 中，也可以通过 `context.Context` 的 value 传递事务对象，使 API 看起来类似 `func DebitBalance(ctx context.Context, ...) error`。但事务对象的存取依赖调用双方的约定，不能由这个签名保证。Go 官方将 context value 定位为跨 API 传递的请求范围数据；事务对象的类型和生命周期仍然需要调用双方自行约定。
:::

#### 为 service 额外注入一个事务 repo 生成器

那么是否有一个类型安全的解决方法呢？在传统的设计中，其实也是有的。

我们仔细分析前述方法的问题来源：具体类型参数让 service **直接依赖** 数据库实现，`Any` 又丢失了类型之间的匹配关系。但实际上，service 不关心上下文的具体行为，usecase 不会调用它的方法，只是作为一个“中转站”。

那么我们的一个解法就是，在 service 层移除对这个参数的 **直接依赖**，而是只关心 E2E 的 **事务版本 repo 的生成**。

根据这个思想，我们可以写出如下的 *初步* 设计。这里的 `WalletRepo` 重新使用最初不带 context 参数的接口：

```rust title="src/repo/generator.rs"
#[async_trait(?Send)]
pub trait RepoGen {
    // 返回内部使用事务上下文的事务版本 WalletRepo
    async fn wallet_repo(&self) -> Result<Arc<dyn WalletRepo>, BaseError>;
}
```

我们在 service 中的使用方法则变成：

```rust
pub async fn transfer_balance(
    generator: Arc<dyn RepoGen>,
    sender_id: i64,
    receiver_id: i64,
    amount: i64,
) -> Result<(), BaseError> {
    // ...

    let wallet_repo_trx = generator.wallet_repo().await?;
    wallet_repo_trx.debit_balance(sender_id, amount).await?;
    wallet_repo_trx.credit_balance(receiver_id, amount).await?;

    Ok(())
}
```

然而，这种解法看似可行，但要落地仍然有不少问题。比如：

- 以需要 `&mut Connection` 的数据库接口为例，多个事务版 repo 对象不能同时直接持有同一连接的独占借用。如果要让它们共享事务，就需要额外的借用或资源协调机制。
- 连接在生成器方法内部取得，并在方法结束时归还连接池，就不能返回借用了它的 repo 代理。
- `wallet_repo` 这样的函数没有提供显式结束事务的接口，也没有用闭包界定业务范围，因此调用方无法通过这个 API 完整表达何时提交或回滚。

看似这种生成器思路也堵死了……吗？实际上，它已经向目标迈出了一大步。在下一节，我将会叙述如何从这个方法，推导出同时满足前述约束的事务上下文注入范式。

:::tip
在 Go 这种没有借用检查器的语言里，可以让多个 repo 包装同一个事务对象，再搭配闭包式 API（下文会提到）管理事务范围。本文继续讨论 Rust 中如何通过类型关系和借用表达这种协作。
:::

### 题外话：为什么基于 Spring Boot 的应用很少体会到事务掣肘

在使用 Spring Boot 的应用中，事务管理通常由 Spring Framework 提供。在常见的命令式 JDBC 事务模型里，Spring 将事务资源绑定到当前线程，数据访问组件通过 Spring 的事务感知机制取得对应的连接，因此 service 不必逐次传递连接参数。

Spring 提供 JDBC、JPA、Hibernate 等集成，MyBatis-Spring 也接入了 Spring 已有的事务管理机制。事务参与关系由框架配置和运行时协调，service 的函数签名不会显式表达这种关系。使用这种方案时，需要保证事务管理器与数据访问组件使用匹配的资源配置。

本文关注的是通过显式参数、关联类型和借用表达事务上下文关系，所以下文不展开这种框架托管的隐式上下文方案。

## 基于关联类型的事务上下文注入

那么，是否有一种优雅的解决方案呢？那自然是有的。在这一小节，我将会一步步推导出如何在编译期确定 transaction 上下文的类型关系，并在运行时完成注入。

### 从生成器方法出发演进

在上一小节的最后，我们说明了朴素的事务 repo 生成器还缺少哪些机制。不过幸运的是，它已经走在了正确的道路上。

我们来一个一个解决它最终遗留下来的问题。

先解决第一个问题。在本文采用的数据库接口中，事务版 repo 需要使用一个 `&mut Connection`。一种处理方式是让一个物理上的对象同时实现不同 repo 的 interface，由这个对象持有连接，各个 action 顺序使用它。

我们把生成出来的聚合对象称为 `RepoProxy`。下面用创建用户及其团队成员记录的例子，展示同一个事务如何提供跨 repo 的能力：

```rust
#[async_trait(?Send)]
pub trait UserRepo {
    async fn create_user(&self, name: &str, email: &str) -> Result<i64, BaseError>;
}

#[async_trait(?Send)]
pub trait MemberRepo {
    async fn create_member(&self, user_id: i64, team_id: i64) -> Result<(), BaseError>;
}

pub trait RepoProxy: UserRepo + MemberRepo {}

impl<T> RepoProxy for T where T: UserRepo + MemberRepo {}
```

```rust title="src/repo_impl/transaction.rs"
pub struct RepoProxyImpl<'c> {
    conn: &'c mut Connection,
}

#[async_trait(?Send)]
impl UserRepo for RepoProxyImpl<'_> {
    // ...
}

#[async_trait(?Send)]
impl MemberRepo for RepoProxyImpl<'_> {
    // ...
}
```

这样，在接口层面就可以通过一个代理调用不同 repo 的能力：

```rust
let repo_proxy = RepoProxyImpl { conn };

let user_id = repo_proxy.create_user(&name, &email).await?;
repo_proxy.create_member(user_id, team_id).await?;
```

随后我们一并解决连接生命周期和事务结束位置的问题。一个事务通常有确定的业务范围，可以用闭包表达。协调器负责取得连接、开启事务并构造 `repo_proxy`，在连接仍然有效时把代理借给闭包使用。

把上述的事务用闭包代码表达即为：

```rust
async move |repo_proxy| {
    let user_id = repo_proxy.create_user(&name, &email).await?;
    repo_proxy.create_member(user_id, team_id).await?;
    Ok::<i64, BaseError>(user_id)
}
```

协调器等待闭包完成后，根据返回的 `Ok` 或 `Err` 提交或回滚，再释放连接。

最后，我们加上一个封装 `repo_proxy` 构造过程和事务管理的 `Coordinator`，并注入 service 层：

```rust title="src/repo/runner.rs"
#[async_trait(?Send)]
pub trait Coordinator {
    type Repo<'c>: RepoProxy;

    async fn run_in_transaction<F, T>(&self, f: F) -> Result<T, BaseError>
    where
        F: for<'r, 'c> AsyncFnOnce(&'r mut Self::Repo<'c>) -> Result<T, BaseError>;
}
```

因此，这个设计就描述了事务的业务执行范围，同时把连接和代理的创建、使用与释放都留在协调器内部。

综上，最终的 usecase 使用方式将类似这样：

```rust
pub async fn register_invited_user<C>(
    coordinator: &C,
    name: String,
    email: String,
    team_id: i64,
) -> Result<i64, BaseError>
where
    C: Coordinator,
{
    coordinator
        .run_in_transaction(async move |repo_proxy| {
            let user_id = repo_proxy.create_user(&name, &email).await?;
            repo_proxy.create_member(user_id, team_id).await?;
            Ok(user_id)
        })
        .await
}
```

### 新范式最终落地

经过一番推导，我们似乎得到了最终答案。但是，如果读者自行尝试实现一下，就会发现一个问题：普通 repo 的接口接受的是 `&self`，而 `RepoProxyImpl` 如果直接使用内部的 `&mut Connection` 执行数据库操作，就需要可变访问 proxy。

注意到，我们可以使用 Rust 中常见的“数据与逻辑分离”的思路修复这个问题，同时为后续的执行逻辑复用提供统一接口。

之前的设计中，`RepoProxyImpl` 既持有执行所需的数据 `&mut Connection`，也承载了执行所需要的逻辑 `impl UserRepo`。现在我们把事务数据独立为 `Context`，由协调器提供它的可变借用；repo 则通过 `&self` 接收这个上下文，只负责执行操作。

拆分后，原有 repo 方法可以增加关联类型 `Context` 和对应参数。不过，我们还希望把操作本身与执行方式分开，让同一操作复用参数和输出定义，并让 usecase 按需组合执行能力。

因此，我们进一步抽象 action：无论是什么 repo，一个操作都可以描述为“通过什么参数，期望得到什么数据”。具体如何执行，则交给另一层接口。因此，我们可以将 action 抽象为 `Oper`：

```rust
pub trait Oper {
    type Output;
}
```

接下来，我们提供 **两种执行方式**：`Run` 由执行器自行管理上下文，`Step` 则使用调用方传入的上下文。本文用 `Run` 表达普通执行，用 `Step` 参与外部协调的事务；接口本身并不禁止 `Run` 在内部开启事务。

```rust
#[async_trait(?Send)]
pub trait Run<O>
where
    O: Oper,
{
    type Error;

    async fn run(&self, oper: &O) -> Result<O::Output, Self::Error>;
}

#[async_trait(?Send)]
pub trait Step<O>
where
    O: Oper,
{
    type Context; // 本文中用于传递事务上下文
    type Error;

    async fn step(&self, context: &mut Self::Context, oper: &O) -> Result<O::Output, Self::Error>;
}
```

:::note
这里把执行失败的 `Error` 定义在 `Run` 和 `Step` 中，`Oper::Output` 只描述成功时的输出。操作参数的构造和校验也可能失败，但不由这个 `Oper` 接口表达。
:::

这样，对于 **一个目标 oper**，我们就可以自由地声明我们的执行方式，一个 repo 的声明方式就会变成：

```rust
pub struct DebitBalance {
    pub wallet_id: i64,
    pub amount: i64,
}

impl Oper for DebitBalance {
    type Output = ();
}

pub struct CreditBalance {
    pub wallet_id: i64,
    pub amount: i64,
}

impl Oper for CreditBalance {
    type Output = ();
}

pub struct CreateUser {
    pub name: String,
    pub email: String,
}

impl Oper for CreateUser {
    type Output = i64;
}

pub struct CreateMember {
    pub user_id: i64,
    pub team_id: i64,
}

impl Oper for CreateMember {
    type Output = ();
}
```

```rust
pub trait WalletRepo: Step<DebitBalance> + Step<CreditBalance> {}

pub trait UserRepo: Run<CreateUser> + Step<CreateUser> {}

pub trait MemberRepo: Step<CreateMember> {}
```

:::tip
实际上，由于 `Run` 和 `Step` 的可组合性，不需要 repo 聚合 supertrait 也是可行的，但是工程上逐个列出约束可能过于繁琐，所以也可以聚合为 repo 单位。聚合本身不保证各个操作使用相同的 Context，具体 usecase 仍需按需声明类型相等关系。
:::

最后，我们更新一下 `Coordinator`（更名为 `Nucl`），它现在应该提供的是 context 而不是完整的 `repo_proxy`：

```rust
// `Step(E)` 表示闭包返回的操作错误，`Backend(BE)` 表示事务管理过程中的错误
pub enum NuclError<E, BE> {
    Step(E),
    Backend(BE),
}

#[async_trait(?Send)]
pub trait Nucl {
    type Context;
    type Error; // 开启、提交或回滚事务时的后端错误

    async fn coord<F, T, E>(&self, f: F) -> Result<T, NuclError<E, Self::Error>>
    where
        F: for<'cx> AsyncFnOnce(&'cx mut Self::Context) -> Result<T, E>;
}
```

最终的成品 service 代码将类似：

```rust
pub async fn transfer_balance<N, R, C>(
    (nucl, repo): (&N, &R),
    sender_id: i64,
    receiver_id: i64,
    amount: i64,
) -> Result<(), NuclError<BaseError, BaseError>>
where
    N: Nucl<Context = C, Error = BaseError>,
    R: Step<DebitBalance, Context = C, Error = BaseError>
        + Step<CreditBalance, Context = C, Error = BaseError>,
{
    // 此处假设调用方已经完成 validate_transfer 参数校验。
    nucl.coord(async move |context| {
        repo.step(
            context,
            &DebitBalance {
                wallet_id: sender_id,
                amount,
            },
        )
        .await?;

        repo.step(
            context,
            &CreditBalance {
                wallet_id: receiver_id,
                amount,
            },
        )
        .await
    })
    .await
}

pub async fn register_invited_user<N, R, C>(
    (nucl, repo): (&N, &R),
    name: String,
    email: String,
    team_id: i64,
) -> Result<i64, NuclError<BaseError, BaseError>>
where
    N: Nucl<Context = C, Error = BaseError>,
    R: Step<CreateUser, Context = C, Error = BaseError>
        + Step<CreateMember, Context = C, Error = BaseError>,
{
    nucl.coord(async move |context| {
        let user_id = repo.step(context, &CreateUser { name, email }).await?;

        repo.step(context, &CreateMember { user_id, team_id })
            .await?;

        Ok::<i64, BaseError>(user_id)
    })
    .await
}
```

此时，repo 使用 `&self`，可变借用集中在传入的 Context 上。两个操作顺序使用同一个上下文，避免了把可变连接藏在共享 repo 内部造成的借用冲突。事务是否真正提交或回滚，仍由 Nucl 的具体实现负责。

#### 全新的 Context 意义

最终，我们又重新在 service 层引入了 Context 这个概念，这是否是问题呢？

自然不是。在事务上下文组装时，信息的依赖关系不会消失，只会移动位置。最终 service 通过泛型 `C` **间接依赖** 上下文，因为它正是 `nucl` 和 `repo` 对接 `Context` 类型的位置，需要声明双方的类型关系，并在运行时传递上下文。

这与前面直接传入具体数据库类型、或擦除为 `Any` 的尝试不同：usecase 无须知道 Context 的具体类型，也无须为它规定数据库操作接口，只需要声明 `Nucl::Context` 与各个 `Step::Context` 都等于 `C`。编译器据此检查上下文类型是否匹配，具体的数据库事务语义则由实现保证。
