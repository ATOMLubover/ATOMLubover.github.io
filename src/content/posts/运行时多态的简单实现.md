## 简述

在 C 这个古老语言中，没有一种内建的多态机制：既没有类似 Go 的运行时多态，也没有类似 Rust 的编译期多态。因此，使用 C 在某些场景下会感到十分掣肘。

为了弥补这一点，本文将介绍一种简单的运行时多态的实现方法，以期一定程度上消解这些场景下的局限性。

## 使用形态分析

依旧，我们先确定最终的期望使用形态，然后再一步步倒推实现的方式。所以我们先给出初步的伪代码示例如下：

```c
// 定义处示意
typedef interface {
    void bark();
} Animal;

// 调用处用法示意
void example(Dog dog, Cat cat) {
    // 底层实现指向 dog
    Animal animal = dog;
    // 期望输出：“大狗叫”
    bark(&animal);
    
    // 然后转而指向 cat
    animal = cat;
    // 期望输出：“老吴老吴“
    bark(&animal);
} 
```

## interface 的底层结构

首先，我们需要确定的是，`Animal` 既然需要作为一个 C 当中的 “类型”，它必然最终要落地为一个 struct，即使目前我们的伪代码中写的是 interface。

然后我们再观察 `example` 当中的代码，不难发现我们先后将两个结构体（`Cat` 和 `Dog`）的对象赋值给了同一个 `Animal` 对象。而 `Cat` 和 `Dog` 的对象大小是很有可能不一样的，且对于作接口的 `Animal` 结构体来说，其大小与实现结构体应当是无关的。

总结就是：

- `Animal` 大小是一个编译期常量，其与运行时关联的实现结构体大小无关。
- `Animal` 固定大小中所包含的 *信息*，需要能够兼容任意大小实现类。

在这两个约束下，`Animal` 的结构就昭然若揭了：它必须是一种指针结构，通过间接引用以同时满足大小固定、任意引用的要求。

## 间接引用实现

那么下一个问题就是，我们需要使用指针引用实现类的什么信息，才可以实现运行时的多态？

我们可以从最终要实现的具体效果来推测，到底指针指向了什么内容。将 `example` 写成静态派发（手动档）的形式：

```c ins={4,8}  del={2-3,6-7}
void example(Dog dog, Cat cat) {
    Animal animal = dog;
    animal.bark();
    dog__bark(&dog);
    
    animal = cat;
    animal.bark();
    cat__bark(&cat);
} 
```

可见，在两次调用 `bark` 之间，我们需要修改两个引用：

- 对实现类的引用：从 `&dog` 修改为 `&cat`。
- 对方法的引用：从 `dog__bark` 修改为 `cat__bark`。

那么 `Animal` 结构体的布局就很明确了，它应该是一个类型擦除的双指针结构：

```c
// typedef interface {
//    void bark();
// } Animal;
typedef struct {
    void* self; // 类型擦除的实现类对象
    void (*bark)(void*); // 方法的函数指针
} Animal;
```

对应的 `example` 真正的代码是：

```c
void example(Dog dog, Cat cat) {
    Animal animal;
    
    {
        animal.self = (void*)&dog;
        animal.bark = dog__bark;
        
        (*animal.bark)(animal.self);
    }
    
    {
        animal.self = (void*)&cat;
        animal.bark = cat__bark;
        
        (*animal.bark)(animal.self);
    }
} 
```

### 简化用宏

我们现在已经在语法层面打通运行时多态了，但是使用起来着实不太顺手，比如定义接口、构造接口对象和调用对应方法都很麻烦。

所以可以定义三个宏来分别解决这三处问题：

```c
#define INTERFACE_DEFINE(NAME, ...)          \
    typedef struct NAME {                    \
        void* self;                          \
        __VA_ARGS__                          \
    } NAME;

#define INTERFACE_CREATE(NAME, IMPL_PTR, ...) \
    ((NAME){ (void*)(IMPL_PTR), ##__VA_ARGS__ })

#define INTERFACE_CALL(OBJ, METHOD, ...) \
    ((OBJ).METHOD((OBJ).self, ##__VA_ARGS__))
```

使用方法为：

```c
INTERFACE_DEFINE(
    Animal,
    void (*bark)(void*);
)

void example(Dog dog, Cat cat) {
    Animal animal;
    
    {
        animal = INTERFACE_CREATE(Animal, &dog, dog__bark);
        INTERFACE_CALL(animal, bark);
    }
    
    {
        animal = INTERFACE_CREATE(Animal, &cat, cat__bark);
        INTERFACE_CALL(animal, bark);
    }
} 
```

:::important
需要注意的是，由于 C 语言类型系统的局限性，`dog__bark` 和 `cat__bark` 函数的第一个参数（recv 参数）只能是 `void* self`，这里无法做到强类型。
:::

:::tip
这种多指针，或者指针 + 辅助元信息的设计一般被称为 “胖指针”。
:::

## 多函数接口优化

然而，上述实现方案的一个问题是，如果我们的接口需要多个方法时，单个方法指针就不够用了。

所以我们自然需要一个新的机制来兼容这种做法。一个朴素的想法是，我们可以让 interface 结构体当中的方法指针不是一个而是多个，比如：

```c
typedef struct {
    void* self;
    void (*bark)(void*);
    void (*walk)(void*);
} Animal;
```

那么这样定义和构造时就会变成：

```c
INTERFACE_DEFINE(
    Animal,
    void (*bark)(void*);
    void (*walk)(void*);
)

void example(Dog dog, Cat cat) {
    Animal animal;
    
    {
        animal = INTERFACE_CREATE(
            Animal, &dog, 
            dog__bark,
            dog__walk    
        );
        INTERFACE_CALL(animal, bark);
    }
    
    {
        animal = INTERFACE_CREATE(
            Animal, &cat, 
            cat__bark,
            cat__walk
        );
        INTERFACE_CALL(animal, bark);
    }
} 
```

不过这样就会有一个虽然不影响正确性，但是依然卡手的小问题：每次调用 `INTERFACE_CREATE` 都需要手动写一长串的函数绑定。

所以我们完全可以简化这一部分。不难意识到，每个实现类都只会有 **一套** 对接口的实现，这就是一个显然可以做成编译期单例的场景：我们可以为每个实现类写一个方法列表，其中存入了所有的具体方法指针。这个列表，就是 **虚函数表**（vtable）：

```c
typedef struct {
    void (*bark)(void*);
    void (*walk)(void*);
} AnimalVirtTab;

typedef struct {
    void* self;
    const AnimalVirtTab* vtab;
} Animal;
```

这样 interface 的实现就不再是用若干个 *内联* 字段存方法，而是只需要一个指向虚表的指针。实现类也不必再定义自己的表类型，直接复用接口的 `AnimalVirtTab`，提供一个编译期单例即可：

```c
// 表项顺序必须与接口声明一致
static const AnimalVirtTab DOG_ANIMAL_VTAB = {
    dog__bark,
    dog__walk
};
```

调用时等价为（以 `Dog` 为例）：

```c
Animal animal = {
    &dog,
    &DOG_ANIMAL_VTAB
};

animal.vtab->bark(animal.self);
animal.vtab->walk(animal.self);
```

### 简化用宏

为了简化和统一，我们还需要更新现有宏，并添加为实现类生成虚表的宏。前一版的三个宏到此作废，下面给出的都是重写后的版本：

其中接口定义、创建和调用宏修改为：

```c
#define INTERFACE_DEFINE(NAME, ...)          \
    typedef struct {                         \
        __VA_ARGS__                          \
    } NAME##VirtTab;                         \
    typedef struct NAME {                    \
        void* self;                          \
        const NAME##VirtTab* vtab;           \
    } NAME;

#define INTERFACE_CREATE(NAME, VTAB, PTR)    \
    ((NAME){ (void*)(PTR), &VTAB })

#define INTERFACE_CALL(OBJ, METHOD, ...)     \
    ((OBJ).vtab->METHOD((OBJ).self, ##__VA_ARGS__))
```

同时添加实现的定义宏，处理虚表的构造：

```c
#define INTERFACE_IMPL(NAME, VTAB, ...)      \
    static const NAME##VirtTab VTAB = { __VA_ARGS__ };
```

最终效果为：

```c
INTERFACE_DEFINE(
    Animal,
    void (*bark)(void*);
    void (*walk)(void*);
)

INTERFACE_IMPL(
    Animal,
    DOG_ANIMAL_VTAB,
    dog__bark,
    dog__walk
)

void example(Dog dog) {
    // ...
    Animal animal = INTERFACE_CREATE(Animal, DOG_ANIMAL_VTAB, &dog);
    INTERFACE_CALL(animal, bark);
    INTERFACE_CALL(animal, walk);
}
```

## 题外话

### 静态与动态

通常来说，“静态” 约等于 “编译期”，“动态” 约等于 “运行时”。两者可以在不同层面上实现同一个机制。

相对于面向值的动态分发，面向类型的静态分发在编译期就完成分发过程，所以在底层编程更关注运行时性能的氛围下，通常会认为静态分发更好。

但这不代表静态分发就是解决一切场景的万能灵药，它也有如下几个可能的问题：

- 对类型系统机制要求极高：大部分语言没有足够完善的类型系统机制完成静态分发所需要的信息传递。
- 单态化导致的二进制膨胀：由于静态分发会将目标（函数/结构体）的每个泛型组合都单态化为独立的结构，这会导致相似的代码在二进制中多份存在。
- 单态化函数过多导致 icache 抖动：一个静态分发函数的多个变体都处于热路径上时会挤压 icache 中其他指令的存储空间，进而可能导致提高 icache miss。

不过后续两个问题都有缓解的手段，通常代码中也很难触碰到这样的极端场景。

最后需要为动态分发证明的是，其实在现代计算机中多一个虚表的两次跳转开销几乎可以忽略不计。比如 C++ 性能最高日志库之一的 `spdlog` 每次格式化都会遍历一遍 `vector<unique_ptr<flag_formatter>>`（`flag_formatter` 是一个抽象类），但这并不影响它的性能强劲。

:::note
注意，C 和 C++ 的 `static` 并不完全是我这里所说 “静态” 的意思。
:::

### 虚表实现的典型语言

大部分语言都有内建的运行时多态，包括 C++、Java 和 Go。比如我上文中的 `example` 其实就是从 Go 的写法转换过来的：

```go
func Example(dog Dog, cat Cat) {
    var animal Animal = &dog
    animal.bark()
    
    animal = &cat
    animal.bark()
}
```

这里就可以直接看出，赋值给 `animal` 值的是指针，而非对象本身。

### 析构安全性

以虚表实现的动态派发有一个好处，那就是 interface 的对象大小是固定的，因此它可以放入一个容器当中。比如，我们可以将多个 interface 的对象放到一个数组当中：

```c
Animal animals[] = { 
    INTERFACE_CREATE(
        Animal, 
        DOG_ANIMAL_VTAB,
        dog__new()
    ),
    INTERFACE_CREATE(
        Animal,
        CAT_ANIMAL_VTAB,
        cat__new()
    )
};
```

然而，我们这种类型擦除的实现方案，会导致我们失去一些 struct 该如何析构的信息。

比如，我们构建了一个 `Readable[]` 数组，它的底层可能是栈上的缓冲区（可以自然回收），也可能是一个文件（需要手动释放对应资源）。然而，我们在类型擦除后，就无法准确知道该如何释放底层 impl 所绑定的资源了。

所以，在这种场景下，我们通常需要为接口额外显式添加一个 `destroy()` 函数，然后在持有所有权的情况下析构时，调用这个函数以完成动态派发下的资源释放。也就是说，`INTERFACE_DEFINE_DROPPABLE` 无非是 `INTERFACE_DEFINE` 里多塞了一个 `destroy` 表项。其使用方法类似如下：

```c
// 隐含一个 `void (*destroy)(void*)` 表项
INTERFACE_DEFINE_DROPPABLE(
    Readable,
    size_t (*read)(void* self, char* buf, size_t size);
)

void destroy_slice(Readable sources[], size_t size) {
    for (size_t i = 0; i < size; ++i) {
        INTERFACE_CALL(sources[i], destroy);
    }
}
```

### `_Generic` 宏

见识比较广的读者可能会见过 C11 引入的 `_Generic` 宏，并且认为这就是属于 C 的（编译期）多态。但很遗憾的是，`_Generic` 宏并不是我们所说面向类型的开放集多态，而是类似于 Rust 的 `match TypeId::of::<...>` 的类型识别机制。

可以从下述例子中理解它的性质与局限性：

```c
// 针对不同类型的具体实现函数
void print_int(int x) { 
    printf("int: %d\n", x); 
}

void print_double(double x) { 
    printf("double: %f\n", x);
}

// 统一的泛型宏接口
#define print(x) _Generic((x), \
    int: print_int,            \
    double: print_double       \
)(x)

int main(void) {
    print(10);    // 调用 print_int
    print(3.14);  // 调用 print_double
}
```

它其实就是一个 match “类型名称“ 字符串的静态分派结构，并且返回值也只是一段文本，而不是一个编译器可以直接处理的带有语义的 AST 节点。这就导致，它完全无法用于类似泛型的编译期派发设计，只能最多用于实现函数的重载；同时它的机制也导致它几乎总是被在宏当中使用，不适合直接在普通 C 代码中裸调用。
