## 简述

在 Web 开发当中，经常需要遇到希望将某些字段或值进行脱敏的情况。无论是因为值是用户的密码，又或者是值是某种需要保护的环境变量，我们通常都希望它们不进入日志、调试输出或序列化结果当中。

为了达到这些目的，最优雅的设计便是让数据自身声明 sensitive，并且融入到整个语言的相应生态当中。接下来我会以 Rust 为例，演示可以完全融入 `Debug` 和 `Display` 生态的一种可配置的自声明式去敏方案。

## 从 `tracing` 的特性出发

为了能够充分理解我们的 sensitive 机制需要融入什么样的生态，我们先探究一下最常见的 `tracing` 库是如何处理日志追踪中的字段记录的。最简便也最常见的日志记录方法是：

```rust
// 忽略 `repo` 等字段
#[tracing::instrument(level = Level::INFO)]
pub async fn login_user(request: LoginUserRequest) -> anyhow::Result<LoginUserResponse> {
    // ...
}
```

对于如上代码，`tracing` 的默认行为会 *最终* `Debug` 的方式输出参数，类似：

```rust
tracing::info_span!(
    "login_user",
    request = ?request,
);
```

因此，后续的所有脱敏，都将围绕着结构化的 `Debug` trait 如何实现展开。

:::tip
即使不使用 `tracing`，使用其他的 log 库，只要只用了类似 `{args:?}` 格式输出的都会有相似的处境，所以以最主流和功能强大的追踪库 `tracing` 切入（即使 `tracing` 的性能和专门的 log 库比不够看）。
:::

## 脱敏的若干种方法

假设 `LoginUserRequest` 当中有需要脱敏的字段，比如：

```rust
pub struct LoginUserRequest {
    pub username: String,
    pub password: String, // 需要脱敏
}
```

如果直接 derive `Debug` 会导致 password 被 `tracing` 记录到日志当中。

一个自然的想法是，我们给 `password` 做一些特殊处理来解决这个问题。以下由繁至简，列举几种常见的做法。

### 手动标记 fields

在 `tracing` 种，可以选择手动跳过某些参数，并显示地要求记录一些数据。那么在上述例子中，利用这种机制可以写出最基础的手动挡实现方法：

```rust del={1} ins={2-6}
#[tracing::instrument(level = Level::INFO)]
#[tracing::instrument(
    level = Level::INFO,
    skip(request),
    fields(username = %username, password = "[REDACTED]")
)]
pub async fn login_user(request: LoginUserRequest) -> anyhow::Result<LoginUserResponse> {
    // ...
}
```

但是显然，这种设计虽然可以编译，但是过于繁琐。假设某个业务字段总是需要被脱敏，且会在多处被使用，那么就需要在每一个调用处都 “手动解构“ 一次，非常地不优雅。

### 使用特殊类型收束

上一个处理方法中，核心问题在于每次调用处都需要写较多的样板代码，那么非常自然地，我们可以想到使用一种自声明的特殊类型，来收束这些样板代码，将多份调用处代码浓缩为一份定义处代码。

比如令 `password` 的类型为特殊类型 `Password`：

```rust
pub struct Password(String);

impl Debug for Password {
    fn fmt(&self, f: &mut Formatter<'_>) -> fmt::Result {
        #[cfg(debug_assertions)]
        {
            self.0.fmt(f)
        }
        #[cfg(not(debug_assertions))]
        {
            f.write_str("[REDACTED]")
        }
    }
}
```

此时的 `tracing::info_span` 在 release 构建下的输出就会自然地屏蔽掉 `password` 的真实值，类似：

```text
login_user{request=LoginUserRequest { username: "lb", password: [REDACTED] }}
```

然而，我们这样写虽然解决了一些样板代码完成了内聚，却会导致需要手动实现 `Debug` trait 并且构建许多 wrapper 类型。为了一懒到底，显然我们还有更加方便的处理方法。

:::tip
在 Go 这类元编程相对较弱的强类型语言中当中，这种方法已经近乎最优（通过构建新 type 并为其实现 `func String() string`）。否则使用 `json:"[REDACTED]"` 这种设计将会失去一些灵活配置 redact 函数的优势，且会引入反射的 overhead。
当然，要表达 sensitive 的最少信息不会消失，只是不同语言的表达方法与途径不同。
:::

### 基于派生宏 & 属性标记的声明式方案

在上一节中，我们已经几乎接近最终解决方法，唯一要解决的就是 `Debug` trait 实现样板代码的问题。

不难意识到，解决样板代码最简单的方案就是使用宏。那么我们究竟该使用普通的声明宏，还是更加复杂的过程宏呢？考虑到面向结构体的声明宏通常都可以转化为派生宏，我们此处采用派生宏来让代码更加内聚并提高可读性。

在使用派生宏后，显然我们希望不用再手写任何 wrapper 或者 `Debug` 实现，而只需要有 **唯一的** 一个业务 model 了。即增强 `LoginUserRequest` 为：

```rust
//
#[derive(SensitiveDebug)]
pub struct LoginUserRequest {
    pub username: String,
    #[sensitive]
    pub password: String, // 需要脱敏
}

// 没有手动实现 `Debug`，也没有其他 wrapper 类型
// 但是 LoginUserRequest 依然获得了一种特殊的
// `Debug` impl（由 `SensitiveDebug` 宏实现）
```

它在 release 构建  `{request:?}` 调用下的输出应该依然是：

```text
request=LoginUserRequest { username: "lb", password: [REDACTED] }
```

:::note
出于篇幅考虑，此处不展开具体的 proc macro 实现方式，仅提供 API 的使用示例。
不过其中有一个实现细节是，`SensitiveDebug` 会为目标结构体实现 `Debug`，所以用户将不能再额外自行实现 `Debug` trait。
:::

## 自定义脱敏函数

读者可能敏锐地意识到，声明式方案将所有的脱敏都内聚到了宏内部，可读性与一致性确实提高了，但是缺少了灵活性。

比如，我们不总是想要完全擦除掉敏感数据，以邮箱为例：

```rust
pub struct Email {
    pub local: String,
    pub domain: String,
}
```

我们希望的擦除效果是 `"***@{domain}"` 而不是 `"[REDACTED]"`

这并非什么大问题，声明式框架可以很轻松地实现这一点，参考 `serde` 的 API：

```rust
#[derive(Serialize)]
pub struct User {
    pub nickname: String,
    #[serde(serialize_with = "serialize_phone")]
    pub phone: String,
}
```

我们可以很轻松地构建出如下新的属性配置：

```rust
#[derive(Debug)]
struct Email {
    local: String,
    domain: String,
}

fn mask_email(email: &Email, f: &mut Formatter<'_>) -> Result {
    write!(f, "***@{}", email.domain)
}

#[derive(SensitiveDebug)]
struct Account {
    #[sensitive(debug = "mask_email")]
    email: Email,
    // ...
}
```

:::note
此处之所以可选配置叫做 `debug` 是因为声明式框架完全可以支持 `SensitiveDebug` 以及 `SensitiveDisplay` 两种派生宏。
另外值得注意的是，此处的 `debug` 指向的函数是强类型的，比如 `email` 的类型必须完全匹配 `&Email`，宏生成的代码最终会通过 Rust 类型系统保证类型安全。
:::

## 总结

在使用上文所提到的声明式方案后，我们将会获得如下几种好处：

- 几乎 0 样板代码的脱敏：不再需要手动实现 `Debug`。
- 高度内聚，可读性良好的实现：不需要分别查看 struct 定义和 `Debug` impl，一切都聚合在结构体定义处。
- 可以自定义扩展的能力：属性标记可以自定义脱敏函数。
- 适配 `Debug` （以及 `Display`）生态：由于 `SensitiveDebug` 的结构体实现了 `Debug`，它可以自由被组合到其他 `Debug` 结构体中，并且总是不会泄漏。
- 零运行时额外开销：相较于普通 `Debug`，`SensitiveDebug` 同样是在编译期即完成函数逻辑的绑定，无须反射等额外信息传递手段介入。

## 题外话：Java 的相似处理思路

在 Java 的 Jackson 中，同样有基于注解类似的处理思路，比如朴素一些的：

```java
public class Account {

    @JsonSerialize(using = MaskEmailSerializer.class)
    private String email;
    
    // ...
}
```

:::note
当然，Jackson 通常处理的是序列化与反序列化（对应 `serde`），不过它的这种自声明式设计，与上述 `SensitiveDebug` / `SensitiveDisplay` 是类似的。
:::

或者加上统一的抽象处理中间件，形成分离的间接式声明 + 处理器范式：

```java
public class Account {

    // 声明 source，但是不直接引用处理器
    @Sensitive(type = SensitiveType.Email)
    private String email;
    
    // ...
}

public class SensitiveProcessor {

    public static Object process(Object object) {
        // ...
    }

    // 实际会被 `SensitiveType.Email` 路由到的处理函数
    private static String maskEmail(String email) {
        int index = email.indexOf('@');
        if (index <= 1) {
            return "***" + email.substring(index);
        }

        return email.charAt(0)
            + "***"
            + email.substring(index);
    }
}
```

其中第一种范式更加贴近 Rust 的声明式处理，静态处理了分发（虽然运行时仍有一定查找开销）；第二种则更依赖反射和注解的相互作用，属于更加 Java-like 的处理办法，通常来说也比依赖 Jackson 序列化更加通用。
